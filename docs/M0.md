# M0: pins and cslib-frontier

## Decision

Assumptions are **propositions stated with
[cslib-frontier](https://github.com/cslib-community/cslib-frontier)'s definitions**, and the core
defines no semantics of its own. Adversaries and reductions are cslib-frontier's uniform strict
PPT programs (`IsPPT`, `IsOraclePPT`, `TwoStage.IsPPT`): a typed program with a certificate that
one probabilistic multi-tape Turing machine (`Turing.MultiTapePTM`) with one polynomial clock
realizes it at every security parameter. Security is asymptotic (`Game.Indistinguishable`,
negligible advantage). Concrete algorithms are expected to be written in mxx and compiled to such
programs (`docs/mxx-ppt-formalization.md`).

This replaces the RV64IM model over riscv-zkvm (and, before it, `opencompl/sail-riscv-lean`).
That model, its dependencies, and every proof about RISC-V binaries were removed; see the git
history before the commit that removed them for the old record of this file.

## Pins

| Dependency | Revision | Notes |
| --- | --- | --- |
| Lean toolchain | `leanprover/lean4:v4.36.0-rc2` | must equal cslib-frontier's |
| cslib-frontier | `d25e68fd262c7aef49179602e784804fb790ced6` (main, 2026-11-15) | the only direct dependency |
| cslib | `ee99dd30bd1a9f466c25a51b39a5cb0bfe4d2342` | through cslib-frontier |
| Mathlib | `69552756cd8a2d2d48763cf7279fd814d6a1224d` | through cslib; Mathlib cache available |

Mathlib and cslib are never pinned separately: they come through cslib-frontier's own pins, and
the toolchain is bumped together with cslib-frontier.

### VCVio is not a dependency

VCVio `main` is on Lean v4.35.0, cslib-frontier on v4.36.0-rc2, and `.olean` files of different
Lean versions do not mix. The core therefore uses cslib's own `OracleComp`, `ProbComp` and
`ProbOracleComp`, which follow VCVio's design (`OracleSpec`, `OracleComp`, `unifSpec`,
`interpret` = `simulateQ`), and states probabilities as `PMF`. A worker library may bring VCVio
back once a common toolchain exists, with a bridge between the two `ProbComp`s.

### Build caches

`lake update` fetches the Mathlib cache. cslib-frontier publishes its build outputs to a Lake
cache service; to download them for the dependency:

```bash
LAKE_CACHE_ARTIFACT_ENDPOINT=https://storage.googleapis.com/complexitylib-lake-cache/a0 \
LAKE_CACHE_REVISION_ENDPOINT=https://storage.googleapis.com/complexitylib-lake-cache/r0 \
  lake cache get --package=cslib-frontier --repo=cslib-community/complexitylib
```

Without it, `lake build` compiles the cslib-frontier modules the core imports.

## Findings

- **Uniformity.** A PPT certificate fixes one finite-control machine over `Bool` and one
  polynomial clock for every security parameter, so a refutation is a uniform algorithm.
- **The PPT calculus.** `fun_prop` and the `ppt` tactic certify programs built from cslib-frontier's
  registered primitives (binary arithmetic, `testBit`, `Matrix.binaryEntry`, bounded-prefix
  queries, `pure`, `bind`). Two kinds of certificate exist: plain (`ComputableInPolyTime`) and
  tidy (`ComputableTidilyInPolyTime`); `fun_prop` moves from tidy to plain, never back, so a
  helper used under a map needs both (`.tidy`, `.of_tidy`). Loops are where it stops: a sum over
  `List.range` with an input-dependent body, or a nested `flatMap`/`map`, has to be assembled by
  hand from `mapWithInput`, `binary_sum`, `flatMapToBitsWithInput` and `mapToBitsWithInput`. Some arithmetic certificates exist only in
  tidy form (`binary_mod'`, in `PolyTime.Nat.BinaryDiv`, which must be imported explicitly).
- **Numerals in submissions.** In `(if b then 1 else 0) • M`, the numerals default to `ℕ`, so the
  scalar action is the ℕ-action, not multiplication in the ring. The values agree, but proofs
  then fail to match; annotate the scalar's type in a submission.
- **`ctorIdx`, `congr_simp`.** Lean v4.36 emits, for every inductive type `I`, a constructor
  index `I.ctorIdx` that is `implemented_by` the unsafe `I.ctorIdx._impl`, and `simp` realizes
  `f.congr_simp` lemmas on demand under the name of the definition it rewrites. The hygiene checks
  exempt both, as they exempt `f._unsafe_rec` and equation lemmas.
- **Lake and the module system.** Mathlib and cslib-frontier use the module system; the core does
  not. Lake warns about this on every module that imports Mathlib; the warning is harmless.
- `native_decide` adds an `axiom` declaration to the module that uses it, so verification rejects
  such solutions with `forbidden_decl` before the axiom check runs.
- Lake writes package names containing `-` as `«cslib-frontier»` in `lake-manifest.json`; the
  Python tooling strips the guillemets.

## Checkers

- **`leanchecker`** ships with the toolchain, but verification does not call it. `leanchecker
  Solution` replays every `Solution*` module in parallel in one process, and on v4.36.0-rc2 it
  segfaults (`lean_name_eq` in `findOLean`, from `replayFromImports`) when two replayed modules
  share imports: each replay frees its imported regions when it ends. `#sigaba_neo_check` replays
  the solution's declarations itself, onto one environment of the other modules.
- **`comparator`** is not used. `SigabaNeo/Trusted/Check.lean` implements the type and axiom
  checks itself.
